# Фронтенд Finmarket-Lab

Статус: описание выбранного стека и план интеграции. Подготовлено 27.09.2026 без проверки репозитория. Примеры ниже не подтверждают наличие соответствующих файлов и API в проекте.

## Задача интерфейса

Первая версия интерфейса должна показывать торговый стакан: покупки, продажи, цены, объёмы и статус получения данных. В дальнейшем к ней можно добавлять графики, результаты исследований и отчёты.

Выбранный стек: React + TypeScript + ECharts. Для разработки и сборки предлагается Vite; данные предоставляет Python-backend с FastAPI.

## Основные понятия

| Технология | Роль |
| --- | --- |
| HTML | Структура страницы |
| CSS | Оформление и расположение элементов |
| JavaScript | Поведение страницы, запросы и обработка данных |
| TypeScript | JavaScript с дополнительной проверкой типов во время разработки |
| React | Компоненты интерфейса и обновление экрана при изменении состояния |
| ECharts | Графики |
| Vite | Сервер разработки и сборка фронтенда |
| Node.js | Среда, в которой запускаются инструменты фронтенда, включая Vite |
| npm | Установка JavaScript-зависимостей и запуск команд проекта |

Для выбранной схемы React-приложение выполняется в браузере. Node.js нужен для инструментов разработки и сборки. Писать отдельный backend на Node.js ради использования React или Vite не требуется.

## React и компоненты

Компонент — часть интерфейса со своей разметкой и поведением. Предлагаемое разделение:

| Компонент | Назначение |
| --- | --- |
| `Orderbook` | Показ покупок и продаж |
| `PairSelector` | Выбор торгового инструмента |
| `ConnectionStatus` | Статус соединения и актуальность данных |
| `DepthChart` | График глубины рынка на ECharts, если он понадобится |

Компоненты получают данные и отображают их. Когда приложение получает новый снимок стакана, оно обновляет состояние, а React обновляет соответствующий интерфейс.

JSX — синтаксис, похожий на HTML, который используется внутри JavaScript-кода React. В TypeScript-файлах с JSX обычно применяется расширение `.tsx`. Инструменты сборки преобразуют этот код в JavaScript для браузера.

## Зачем нужен Vite

Vite выполняет две основные задачи: обслуживает фронтенд во время разработки и собирает файлы для публикации.

При разработке он запускает локальный сервер, обрабатывает исходники и зависимости, отслеживает изменения. После сохранения файла браузер быстро получает обновление. Для работы с React используется соответствующий плагин.

Vite не является редактором кода. Код редактируется, например, в VS Code; Vite обеспечивает его подготовку и загрузку в браузер. Это и подразумевается под удобством разработки.

Обновление кода через Vite и получение рыночных данных — разные процессы. Стакан обновляется благодаря сообщениям backend, даже когда исходники приложения не меняются.

## Как frontend получает данные

В локальной конфигурации предлагаются два адреса:

| Адрес | Назначение |
| --- | --- |
| `http://localhost:5173` | Vite: страница и файлы фронтенда |
| `http://127.0.0.1:8000` | Uvicorn + FastAPI: API и поток данных |

Порты — пример договорённости проекта; фактические значения определяются настройками запуска.

Последовательность работы:

1. Браузер получает страницу и JavaScript от Vite.
2. В браузере запускается React-приложение.
3. JavaScript-код приложения запрашивает данные у backend.
4. FastAPI вызывает Python-логику и возвращает данные.
5. Приложение обновляет состояние и отображение.

FastAPI не требует React или Vite: к API может обращаться любой подходящий клиент. Vite также не зависит от FastAPI.

### HTTP и WebSocket

HTTP подходит для отдельных запросов: проверить доступность API, получить снимок или список инструментов. WebSocket позволяет держать соединение открытым и передавать новые снимки по мере появления.

Для начала предлагается передавать в браузер полные подготовленные снимки. Поддержание корректного состояния биржевого стакана остаётся на backend. Это упрощает первую реализацию клиента.

### Прокси Vite

Во время разработки Vite может пересылать API-запросы в FastAPI. Браузер обращается к тому же адресу, с которого загружена страница, а Vite работает посредником.

Пример будущего `frontend/vite.config.ts` для процессов, работающих на одной машине:

```ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  server: {
    port: 5173,
    strictPort: true,
    proxy: {
      '/api': {
        target: 'http://127.0.0.1:8000',
      },
      '/ws': {
        target: 'http://127.0.0.1:8000',
        ws: true,
      },
    },
  },
});
```

Пути сохраняются: запрос `/api/health` попадёт в маршрут `/api/health` backend. Эти маршруты ещё необходимо реализовать. `strictPort` заставляет Vite сообщить о занятом порте вместо автоматического выбора другого.

Если Vite и backend работают в разных Docker-контейнерах, `127.0.0.1` внутри Vite-контейнера указывает на этот же контейнер. Тогда адрес назначения нужно заменить на доступный адрес backend, например имя его сервиса в общей сети Compose. Настройки прослушивания и публикации портов тоже зависят от размещения процессов.

### Прямой доступ и CORS

Браузер может обращаться к FastAPI напрямую. Но адреса с разными портами считаются разными origin, даже на одном компьютере. Для таких HTTP-запросов backend должен разрешить конкретный origin фронтенда через CORS.

При использовании прокси Vite браузер отправляет HTTP-запрос на свой origin. Разрешать все origin ради локальной разработки не требуется. CORS не заменяет авторизацию, а проверка origin для WebSocket рассматривается отдельно.

## Разработка, сборка и размещение

Следующие команды применимы после создания `frontend/package.json`, установки зависимостей и настройки соответствующих scripts. Это ориентир, а не проверенная инструкция запуска текущего репозитория.

| Команда из `frontend/` | Назначение |
| --- | --- |
| `npm install` | Установить зависимости |
| `npm run dev` | Запустить сервер разработки Vite |
| `npm run build` | Выполнить настроенную сборку, обычно с результатом в `dist/` |
| `npm run preview` | Локально посмотреть результат сборки |

Фактическое содержание команд задаётся в `package.json`. Vite преобразует TypeScript, но сам по себе не выполняет полноценную проверку типов. Её нужно запускать отдельно или включить через `tsc` в команду сборки.

После сборки подготовленные файлы можно отдавать через веб-сервер или статический хостинг. Сервер разработки Vite и `vite preview` не предназначены для постоянного обслуживания пользователей.

Прокси из `server.proxy` действует при разработке. Для опубликованной версии маршрутизацию `/api` и `/ws` нужно настроить на сервере размещения либо указать отдельный адрес backend. Настройки Vite не превращаются автоматически в прокси опубликованного сайта.

## Предлагаемая организация фронтенда

| Путь | Назначение |
| --- | --- |
| `frontend/src/components/` | Компоненты интерфейса |
| `frontend/src/api/` | HTTP-запросы и работа с WebSocket |
| `frontend/src/types/` | Общие типы данных |
| `frontend/src/styles/` | Общие стили, если понадобятся |
| `frontend/src/App.tsx` | Основной компонент |
| `frontend/src/main.tsx` | Подключение приложения к странице |
| `frontend/vite.config.ts` | Настройки Vite |
| `frontend/package.json` | Зависимости и команды |

На старте достаточно нескольких файлов. Делить их на каталоги стоит по мере появления самостоятельных частей.

## Правила первой реализации

- Начать с фиксированных данных, затем подключить HTTP и WebSocket.
- Показывать загрузку, ошибку, отсутствие данных и потерю соединения.
- При отключении не выдавать последний снимок за актуальный.
- Закрывать WebSocket и освобождать экземпляр графика при удалении соответствующего компонента.
- Отделять получение данных от их отображения.
- Ограничивать частоту отрисовки при необходимости; пропускать можно готовые снимки, но не изменения, необходимые для восстановления стакана.
- Не помещать секреты в frontend: его код и включённые в сборку значения доступны пользователю браузера.

## Почему предлагается Vite

Для проекта нужны React, TypeScript, быстрый просмотр изменений и сборка фронтенда. Vite покрывает эти задачи с небольшим количеством начальных настроек. Backend на Python сохраняется.

Альтернативы включают Webpack с дополнительной настройкой, Parcel и Rsbuild. Проценты из опросов разработчиков не являются долей всех проектов и быстро устаревают, поэтому не используются как основное обоснование выбора.
